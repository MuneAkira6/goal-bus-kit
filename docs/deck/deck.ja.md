# 長命バス方式
## 無人で goal を回す

チケットの束を渡すと、自分で走り切り、あとから帳尻を確かめられる。

4 つの段階で説明します。各段階に、そのままコピーして使えるプロンプトを付けています。

<!-- 話す内容：今日のゴールは「明日から自分の長い作業で試せる」こと。仕組みの細部より、なぜそうするのかを持ち帰ってもらう。 -->

---

## 全体像

| 段階 | あなたが打つもの | 起きること |
|---|---|---|
| 1. 単一の goal | `/goal` と完了条件 | ターンの終わりごとに達成を判定し、未達なら続ける |
| 2. 複数の goal | goal ごとの指示 | 半日単位で区切って進める |
| 3. 長命バス | 「G1 が終わりました」 | 全体を知る会話が審査し、次の指示を書く |
| 4. 無人 | 閂のファイルを 2 つ作るだけ | hook がつなぎ、止まったら人を待つ |

人の関わりは、段階が進むほど一行ずつ減っていきます。

---

## 出発点：大きなプロンプト 1 つは、4 通りに壊れる

1. **コンテキストが失われる**：長くなると、最初の約束を忘れる
2. **基準がずれる**：途中から「これで十分」の水準が下がる
3. **結論を検証できない**：「確認しました」の中身が分からない
4. **手戻りが大きい**：間違いに気づくのが最後

共通点は、どれもエラーにならず「完了しました」と報告されることです。

---

## 段階 1：単一の goal

```text
/goal specs/my-task/PROGRESS.md の G1 の表で、すべての AC に判定と引用つきの証拠を書く。
判定は PASS / FAIL / BLOCKED / DEFERRED のいずれか。確信がなければ BLOCKED。
```

ターンが終わるたびに達成を判定し、未達なら会話に引き戻します。

---

## 天井：判定者は会話しか読まない

- `/goal` の評価者は小さなモデルで、ツールを呼びません
- 判定表のファイルは読めず、引用が本物かも確かめられません
- 「確認しました」と書かれていれば、それを信じるしかありません

プロンプトの工夫では、この天井は越えられません。

---

## 手当て：「完了」をファイルに移す

- **判定表**（PROGRESS.md）：AC ごとに判定と証拠
- **検査スクリプト**（証拠門）：ターンの終わりごとにファイルを読み、証拠のない PASS があればターンを終わらせない
- 引っかかったときは、具体的な問題を会話に返す

```text
PASS なのに証拠が空 / 引用符がない / 「問題なし」だけ → やり直し
FAIL なのに「期待 / 実際」の形でない → やり直し
```

---

## 証拠の規律

| 判定 | 必要なもの |
|---|---|
| PASS | 実際に観察したものの引用（出力、画面の文言、指紋） |
| FAIL | 「期待 X / 実際 Y」 |
| BLOCKED | 何が足りないか |
| DEFERRED | 何の決定を待っているか |

**BLOCKED は減点しません。減点するのは捏造です。** 確信がないまま PASS に丸めるくらいなら、BLOCKED と書いてもらいます。

---

## 段階 2：goal に分ける

- 1 つの goal は半日程度を目安にする
- G0 は環境の確認と契約の凍結に充て、製品コードは書かない
- G1 は仕組みを確かめられる最小の変更にする
- 最後の goal は、突き合わせ、契約の AS-BUILT 化、変更一覧にする

```text
今回の goal は G1。範囲は〇〇。完了条件は PROGRESS.md の G1 の表がすべて埋まること。
禁止事項：ブランチを触らない、commit しない、無関係な既存の問題は直さず記録する。
```

---

## ボトルネックが人に移る

goal の境界ごとに、人が次の指示を書き直すことになります。

- 前の goal で分かったこと（環境の事実、踏んだ罠）を反映しなければならない
- 新しく立ち上げた会話には書けない。経緯を知らないから
- 結局、人が記憶を頼りに伝言している

---

## 段階 3：長命のバス

- **goal 包を書いた会話そのもの**を、決まった session id で何度も起こします
- バスがすること：審査する、裁決（PASS / REJECT / ESCALATE / DONE）を出す、次の指示を書く
- 新しい審査役にはできないこと：**前の goal の証拠を使って、今の goal に反論する**

```text
G1 が終わりました。PROGRESS.md の G1 を BUS-PROTOCOL.md に沿って審査し、
最後に BUS-VERDICT と BUS-NEXT のブロックを付けてください。
```

---

## バスが書く指示の中身

runbook の該当手順に、前の goal から学んだことが足されます。

- 「環境はもう立ち上がっているので、立て直さないこと」
- 「前回の比較では 2 つの条件のデータの状態が違っていた。揃えてから取り直すこと」
- 「この AC は G1 で証明済みなので引用でよい」

実際の運用では、runbook に書かれていない指示が半分ほどを占めていました。

---

## それでも、伝言しているのは人

作業はエージェントがしているのに、「G1 が終わりました」と打つのは人のままです。

夜のあいだは、誰も伝言しません。

---

## 段階 4：無人にする

Stop hook を 2 つ置きます。2 つの会話は、ファイルとスクリプトを通してしか話しません。だから途中で切れても、続きから始められます。

- **証拠門**：証拠のない判定を数秒で差し戻す（バスは起こさない）
- **リレー**：goal の途中は表の空欄を数えて「続けて」と返し、境界でバスを起こし、裁決を解析して次の指示を渡す

---

## 判定の流れ

```text
ワーカーのターン終了
 ├─ goal の途中     → 空欄を数えて「続けて」
 └─ G1 COMPLETE     → 表は埋まった? 証拠門は通る?  → いいえ：安く差し戻す
                      → はい：バスを起こす → PASS：次の指示 / REJECT：直す点
                                           → ESCALATE・DONE・異常：止まって人を待つ
```

安いチェックを先に置き、費用のかかる審査はきれいな境界でだけ行います。異常時は必ず止まります。

---

## 発車

```bash
bash .claude/hooks/goal-bus.sh --seed
touch specs/my-task/.gate-on specs/my-task/.relay-on
bash .claude/hooks/bin/start-worker.sh --file specs/my-task/g0-instructions.md
```

閂のファイルを消せば、いつでも手動の運用に戻れます。

---

## 実務での数字（実測値・コードは非公開）

- 運用 18 回（2026 年 8〜9 月）
- 最初の本番運用：6 goal、裁決 9 回（うち REJECT 3 回はいずれも実際の問題）、判定 100 行で FAIL 0、人の介入は 1 回
- UI カバレッジの 12 ストリーム：判定 446 行、バスの起床 113 回
- 最長の無人区間：7 ストリームを自動で引き継ぎ、16 時間 37 分

バス側の費用は CLI が報告する cost_usd（API 換算値）で、実際の支出ではありません。

---

## バスが止めた回帰

- ログイン後の着地点を変えたところ、別の場所にハードコードされていた遷移が壊れた
- ワーカーの報告は「4 ファイル 10 箇所」。バスは自分で数え直し、**5 ファイル 11 箇所**を見つけた
- ワーカーは修正を最後の goal に回そうとしたが、バスは「この goal で入れた回帰は、この goal で直す」と差し戻した

マージ前に止まりました。この方式の価値が一番よく表れた場面です。

---

## 使うべきとき、使うべきでないとき

**使う**：複数のチケットと日にまたがり、すべての AC を観察で判定でき、無人の権限設定が許される環境で、人が非同期に関われるとき

**使わない**：探索的な設計、goal の途中で人の判断が頻繁に要る作業、小さな修正一つ

自問の一言：**「どの AC についても、何を観察すれば証明できるか言えるか」**

---

## 塞がっていない穴（隠しません）

1. **バスが中身を見ずに通す**：機械では防げません。審査の全文を残し、人が抜き取りで監査します
2. **ESCALATE は誰にも届かない**：台帳を書いて止まるだけです
3. **閂を消されると hook は黙る**：自分が動いていないことを報告できません

2 と 3 は同じ理由です。hook は「ターンが終わったとき」にしか動かないので、「何も起きていない」ことを検出できません。
