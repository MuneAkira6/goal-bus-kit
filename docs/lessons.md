# 教訓 30 件：どの防護も、実際に何かが壊れたところから来ている

> **English summary** — Thirty lessons from running unattended goal relays for real, generalised and
> rewritten. Each one reads symptom → cause → guard → where the guard lives in this kit, and names the
> test labels that protect it (`[Ln]` in `hooks/selftest/*.sh` and `tests/*.sh`). Most of them are
> about failures that make no noise: the relay stops, or keeps going blind, and nothing complains.

どの教訓も、実務でこの方式を運用する中で起きた出来事を、特定の案件から切り離して書き直したものです。各項目は「症状 → 原因 → 防護 → このツールキットでの実装」の順に並べ、守っているテストのラベル（例 `[L15]`）を添えました。`bash tests/lesson-coverage.sh` は、30 件すべてに少なくとも 1 つのテストがあることを確かめます。

読むときの目印として、大半の教訓は「音のしない失敗」についてのものです。止まっても何も鳴らない、あるいは見えないまま進み続ける、という形の失敗です。

---

## L1 hook の timeout は、スクリプト自身の最悪の所要時間より長くする

- **症状**：審査は最後まで走って費用も発生したのに、裁決が台帳に残らない。
- **原因**：Claude Code が hook の timeout で hook を先に止めた。審査の後に交代（引き継ぎ書き＋新しいバスの起動）が続くと、最悪で単発の審査の 3 倍近い時間がかかる。
- **防護**：settings の timeout を `REVIEW_TIMEOUT + 2 × HANDOFF_TIMEOUT + 60` より大きくする。交代には審査とは別の短い時間枠を与える。
- **このキットでは**：`bus.config.sh` に式を書き、`settings.hooks.json` は 2520 秒。`goal-bus.sh --status` が実際の settings を読み、足りなければ警告する。`[L1]`

## L2 コンテキストはトランスクリプトの最後の usage で測る

- **症状**：最初の審査の直後に、まだ空いているはずのバスが交代させられた。
- **原因**：ヘッドレス実行の結果 JSON にある usage は、その実行の全ターンの合計で、キャッシュ読み込みを毎ターン数え直している。実測で約 10 倍に膨らんでいた。
- **防護**：トランスクリプトの最後の usage（input + cache read + cache creation）を使う。読めなければ 0 とし、0 であることを台帳に大きく書く（0 のままだと交代が永遠に起きない）。
- **このキットでは**：`tokens_in_transcript()`。読めなかったときは BUS-LOG に警告行が入る。`[L2]`

## L3 jq の `//` は false を「値なし」として扱う

- **症状**：成功した呼び出しが、すべて失敗として扱われた。
- **原因**：`.is_error // true` と書くと、`is_error: false` が「値なし」とみなされて true に置き換わる。
- **防護**：真偽値は `== false` のように明示的に比べる。
- **このキットでは**：`call_ok()`。`is_error` が欠けているときも成功とはみなさない。`[L3]`

## L4 利用上限の判定より先に「応答を受け取れたか」を判定する

- **症状**：代金まで発生した PASS の審査が捨てられ、次の goal の指示ごと失われて、リレーが数時間止まった。
- **原因**：stderr を同じ出力に取り込んでいたので、成功した実行の後ろに出た利用上限の案内行が「上限で失敗」と判定された。
- **防護**：まず完全な応答を受け取れたかを確かめる。受け取れていれば、上限の案内は雑音として扱う。
- **このキットでは**：`hit_usage_limit()` は `call_ok()` が真なら必ず偽を返す。結果の JSON 行は、前後の stderr の中から探し出す（`result_json()`）。`[L4]`

## L5 失われた裁決はトランスクリプトから回収する。もう一度払わない

- **症状**：hook の判定ミスや解析失敗で、裁決が台帳に残らなかった。
- **原因**：hook が応答を捨てても、審査の本文はバスのトランスクリプトに残っている。
- **防護**：審査をやり直さず、トランスクリプトの最後の応答を取り出して台帳に補記する。
- **このキットでは**：`goal-bus.sh --recover [session-id]`。失敗や上限の経路のメッセージは、どれもこのコマンドを案内する。`[L5]`

## L6 Stop hook はすべての会話で動く。守衛が 2 つ要る

- **症状**：人が開いた別の会話や、バス自身が、現在の goal に引き込まれた。
- **原因**：Stop hook はリポジトリ内のどの会話のターン終了でも発火する。
- **防護**：(1) バス自身の session id は駆動しない。(2) 進捗行を出している会話だけをワーカーとみなす。さらに、hook が起動した子の会話（`GOALBUS_NESTED=1`）は両方の hook が素通しする。
- **このキットでは**：`goal-bus.sh` 冒頭の守衛と、BUS-PROTOCOL 第 0 節の説明。`[L6]`

## L7 goal の範囲は h2 の見出しだけで区切る

- **症状**：最後の goal がいつまでも COMPLETE にならなかった。
- **原因**：goal の後ろに置いた付録の表が、最後の goal の未判定行として数えられていた。
- **防護**：goal の区間は `## G<n>` から次の `## ` 見出しまで。`###` は goal の中に残り、goal 以外の h2 は区間を閉じる。
- **このキットでは**：`tables.awk` と PROGRESS テンプレートの冒頭コメント。`[L7]`

## L8 Stop hook から /goal は起動できない。hook 自身が駆動役になる

- **症状**：PASS の後、ワーカーが次の goal の最初のターンで止まった。
- **原因**：Stop hook が返すテキストは会話に注入されるだけで、スラッシュコマンドとしては展開されない。
- **防護**：goal の途中のターンは、hook が PROGRESS.md の未判定数を数えて「続けて」と返す。BUS-NEXT には `/goal` ではなく普通の指示を書く。暴走止めとして goal ごとのターン上限を設ける。
- **このキットでは**：`goal-bus.sh` の goal 途中の経路と `TURN_LIMIT`。`[L8]`

## L9 引用型の判定には、タスクの外を指す 2 つ目の引用を要求する

- **症状**：「上流で証明済み」とする判定が、実質的に何も確かめられずに通っていた。
- **原因**：2 つ目の引用の目印が、タスク自身の PROGRESS.md でも満たせる文字列だった。
- **防護**：2 つ目の目印は必ずタスクのディレクトリの外にある出典を指すものにする。
- **このキットでは**：`CITE_VERDICT` / `CITE_MARK_A` / `CITE_MARK_B`。テストのフィクスチャは設定値から作るので、どんな設定でも意味を保つ。`[L9]`

## L10 無人運転は bypassPermissions ＋ deny。acceptEdits では止まる

- **症状**：夜間の実行が、最初のシェルコマンドの許可待ちで止まっていた。
- **原因**：acceptEdits が自動で許可するのはファイル編集だけ。
- **防護**：bypassPermissions に deny リストを組み合わせる。deny は allow より先に評価され、bypass でも飛ばされず、バスのヘッドレス実行にも引き継がれる。commit・push・PR は人の関門として deny に入れる。ブランチ作成には機械的な防護がないことも明記する。
- **このキットでは**：`templates/settings.hooks.json`。`[L10]`

## L11 長期メモは要約ではなく補集合

- **症状**：交代の後、新しいバスが前任と同じ指摘をしなくなった。
- **原因**：長期メモが台帳の要約になっていて、裁決にならなかった判断（疑い、ワーカーの癖、自分で確かめたこと）が残っていなかった。後の実測で訂正された値が古いまま残っている項目もあった。
- **防護**：長期メモには、ファイルから読めないものだけを書く。訂正されたら書き直す。
- **このキットでは**：`templates/BUS-MEMORY.md` と BUS-PROTOCOL 第 5 節。`[L11]`

## L12 交代はきれいな PASS の境界でだけ行う。失敗したら旧バスを使い続ける

- **症状**：差し戻しの途中で交代が起きると、差し戻しの文脈が失われる。
- **原因**：交代のタイミングを選んでいなかった。
- **防護**：コンテキストが閾値を超え、しかも裁決が PASS のときだけ交代する。引き継ぎ、起動、切り替えのどこかで失敗したら、旧バスのまま続けてそのことを伝える。
- **このキットでは**：`hand_over_bus()`。REJECT の最中には交代しない。`[L12]`

## L13 異常はすべて「止まって人を待つ」に倒す

- **症状**：想定外の状態で強行すると、壊れた状態が次の goal に持ち越される。
- **原因**：異常時の既定の動作が「続行」になっていた。
- **防護**：`set -e` を使わず、失敗はすべて明示的に扱う。設定がない、セッションがない、ロックが取れない、上限に達した、解析できない、呼び出しに失敗した、といった場合はいずれも止まって人を待つ。現在の goal はファイルから導くので、止まっても一言「続けて」で再開できる。
- **このキットでは**：両 hook の全経路。設定ファイルがなければ hook は完全に何もしない。`[L13]`

## L14 バスの手抜き（中身を見ずに通すこと）は、機械では防げない

- **症状**：「問題なさそうです」で PASS が出ても、誰も気づかない。
- **原因**：証拠門は証拠の形しか見られず、審査の質は見られない。
- **防護**：人が抜き取りで監査する。見るべき兆候（一人称の確認がない、ワーカーの報告の言い換えだけ、注意点のない PASS、手順のない REJECT など）をチェックリストにする。バスには「自分で確かめたこと」を長期メモに毎回書かせる。
- **このキットでは**：runbook 第 6 節の監査チェックリスト、BUS-REVIEWS.md（全文の記録）、BUS-PROTOCOL の「良い裁決の形」。`[L14]`

## L15 ワーカーの署名は、行頭に固定した意味のある形にする

- **症状**：バスが報告の中で「PROGRESS:」に続けて行番号を書いたところ、次のターン終了で hook がバスをワーカーとして駆動した。従っていれば、審査する側が自分で判定を書くことになっていた。
- **原因**：署名の判定が、単なる部分文字列の一致だった。
- **防護**：その行自体が `PROGRESS: <goal名 または BLOCKED>` で始まっていること（先頭の Markdown の飾りは許す）。文中の言及や接頭辞の話題は署名とみなさない。
- **このキットでは**：`WORKER_LINE_RE`。hook とテストが同じ変数を使う。事故の形を含む反例をテストに入れている。`[L15]`

## L16 「どこまで進んだか」と「実際に審査されたか」を並べて見せる

- **症状**：ある goal の表が埋まったのに境界行が出ず、その goal が審査されないまま次へ進んだ。状態表示からは分からなかった。
- **原因**：現在の goal は「空欄のある最初の goal」として導かれるので、境界がないと黙って次の goal を指す。
- **防護**：裁決のたびに `ruled_<goal>` を記録し、状態表示に「審査済み」と「表は埋まったのに裁決がない」を並べる。後者には 3 つの読み方（まだ実行中／境界が抜けた事故／別の goal 名で記帳された）を添える。hook が一度も動いていないときは、疑いを表示しない。
- **このキットでは**：`--status`。さらに、表が埋まって裁決のない goal があれば、hook がその goal の審査を強制する（`unreviewed_goal()`）。`[L16]`

## L17 BLOCKED の境界行は goal 名を受け付け、その行から記帳先を取る

- **症状**：ワーカーが `PROGRESS: G6 BLOCKED …` と書くと、境界として認識されなかった。
- **原因**：BLOCKED の正規表現が goal 名なしの形しか受け付けていなかった。goal 名なしの場合は記帳先を推測するしかなく、推測は外れることがある。
- **防護**：goal 名の有無のどちらも受け付け、記帳先は境界行そのものから取る。本文中に引用された別の goal の行に記帳先を奪わせない。
- **このキットでは**：`line_kind()` / `line_goal()`。判定するのはメッセージの最後の署名行。`[L17]`

## L18 バスを起こすコマンドは、スクリプト全体で 1 か所だけに置く

- **症状**：人が手で打ち直した起動コマンドでバスは普通に応答したが、ファイルを一切読み書きできず、「権限が絞られた」と誤った原因を報告した。
- **原因**：打ち直しの際に `--allowedTools` と `< /dev/null` が落ち、子の目印が別の書き方になっていた。どれも黙って劣化する。
- **防護**：起動コマンドは 1 か所で組み立てる。人の入口が必要なら、その 1 か所を呼ぶサブコマンドを用意する。
- **このキットでは**：`claude_call()`（バス側）と `worker_call()`（ワーカー側）。人の入口は `--notify`。構造テストで呼び出し箇所の数と 3 つの部品を検査する。`[L18]`

## L19 護欄は時間とともに進む量にアンカーし、一度わざと発火させる

- **症状**：3 つの別々の失敗が、実は同じ病気だった。(1) 実行に必要な数より低い上限。失敗のたびに数がリセットされるので、一度も発火しないまま緑に見えていた。(2) プロセス名で生死を判定する停止検知。何日も前のゾンビプロセスがいるせいで条件が常に偽になり、リレーが黙って止まった。(3) ソースに固定した goal 名と追記専用の台帳を組み合わせた予算の関門。その goal が終わると、永遠に閉じたままになった。
- **原因**：判定の元になる量が、時間とともに進まない。
- **防護**：時間とともに進む量（単調に増える量の差分）にアンカーする。導入時には発火の条件をわざと作り、実際に鳴ることを確かめる。一度も鳴るのを見ていない護欄は、緑であっても何も語らない。
- **このキットでは**：上限ごとの「発火させる」テスト（`manufactured`）、古い引き継ぎ書を新しいものと取り違えない指紋の比較、`watch.sh` の単調増加量による停止検知。`[L19]`

## L20 ターンは必ず境界行で終える。長い作業を切り離してターンを終えない

- **症状**：ワーカーが報告文でターンを終え、誰も起こされないまま 77 分止まった。切り離して走らせていた作業の結果は、誰にも回収されなかった。
- **原因**：hook は「ターンの終わり」にしか動かず、境界行がなければ何もしない。
- **防護**：ワーカーの指示書に「ターンは必ずどれかの行で終える」「長い作業は 1 回の同期待ちで待ち、ターンをまたいでポーリングしない」と書く。hook も goal の途中で毎回それを繰り返す。
- **このキットでは**：goal-brief の「Turn rhythm」節と、goal 途中の経路のメッセージ。判定には最後の署名行を使う。`[L20]`

## L21 「ワーカー 1 つ」はプロセスの中の設定にすぎない

- **症状**：並行して走らせたテストのログの大半が無効になった。偽の失敗は正常なスタックトレースを持ち、本物の欠陥と見分けがつかなかった。
- **原因**：テストランナーの並列数の設定は、1 つのプロセスの内側しか縛らない。
- **防護**：長いバッチは直列に流す。前のバッチの集計行が出てから次を始める。待ちの条件は「ログが静かになった」ではなく集計行に置く。
- **このキットでは**：goal-brief の「Run batches one at a time」。`[L21]`

## L22 hook は人に知らせられない。届く通知チャネルもなかった

- **症状**：止まったことを誰も知らない。
- **原因**：Stop hook はターンが終わるときにしか動かない。止まるというのは「どのターンも終わらない」ことなので、hook は構造上それを検出できない。手元の環境で試した 7 種類の通知チャネルのうち、4 種類は「成功した」と返しながら何も届けず、確実に届いた 1 種類は作業の流れに合わず採用しなかった。
- **防護**：通知の穴は開いたままにしておき、解決済みとは書かない。届くことを確認できていないチャネルはつながない（鳴らない警報は、緑に見える護欄と同じ害がある）。検出器を作るなら hook の外で常駐させ、単調増加量の差分にアンカーする。
- **このキットでは**：通知の仕組みは同梱しない（テストで確認）。`watch.sh` は標準出力にだけ出す。`docs/method.md` に穴を明記。`[L22]`

## L23 ヘッドレスのワーカーでは、ターンの終わりがプロセスの終わり

- **症状**：「条件がそろったら監視が呼び戻してくれる」と言い残して、ワーカーのプロセスが終了した。
- **原因**：駆動役のいない `claude -p` の形態には、呼び戻す仕組みが何もない。
- **防護**：その形態の指示には「ターンを終えるとプロセスが終わる。待つときはすべて、このターンの中で 1 回の同期待ちで待つ」とはっきり書く。死んだら `--resume` で文脈ごと続きから再開する。
- **このキットでは**：`docs/method.md` のリモート形態の節、`watch.sh` が表示する再開コマンド、`start-worker.sh --resume`。`[L23]`

## L24 共有環境の占有確認は、マシンと人をまたいで行う

- **症状**：発車前の確認をすべて通した 1 分後に、別の人が同じ環境でテストを始め、実行が重なった。
- **原因**：発車の瞬間の確認では、その後に始まるものは見えない。
- **防護**：発車前に、すべての作業ツリーとマシンで閂（有効化フラグ）と実行中のプロセスを確かめ、手作業の人がいないかも確かめる。さらに、共有環境に書き込むたびに、その直前にも確かめる。他人のプロセスは止めずに待つ。
- **このキットでは**：runbook 第 0 節と `docs/method.md`。`[L24]`

## L25 awk の実装も仕組みの一部

- **症状**：まったく同じスクリプトなのに、Ubuntu 上では証拠門が何も検出せず、状態表示は空の表を見て「すべて判定済み」と言った。実行時にはどんな症状も出なかった。
- **原因**：Ubuntu の既定の awk（mawk）は区間正規表現に対応しておらず、表の区切り行が一度も一致しなかった。解析器は「何も見えない」側に失敗するので、黙って素通しになる。
- **防護**：hook を走らせるマシンそのもので、両方の自己テストを発車前に通す。このキットでは正規表現を移植可能な形に書き、gawk と mawk の両方でテストする。
- **このキットでは**：`tables.awk` は区間正規表現・POSIX 文字クラス・gawk 専用関数を使わない。`GOALBUS_AWK` で実装を切り替えられ、CI は gawk と mawk で走る。`[L25]`

## L26 別のエージェントの出力を読む判定は、本物の出力で一度確かめる

- **症状**：ストリームの完了を判定する関門が、台帳にない文字列を探していて、一度も開かなかった。自己テストは緑のままだった。
- **原因**：テストのフィクスチャを、実際の出力ではなく「こう書くはずだ」という想像で作っていた。本物の裁決行は太字や箇条書きで飾られていた。
- **防護**：他者の出力を解析する処理は、本物の成果物で一度確かめる。飾りを許容し、最後の一致を採る（最初の一致は、説明のために引用された行を拾って偽の PASS になりうる）。
- **このキットでは**：`read_verdict()` / `read_next_block()`。`watch.sh` のテストは、手書きではなく hook が実際に書いた台帳を読む。テンプレートの例文も本物のパーサーで検査する。`[L26]`

## L27 止まり方は 3 種類あり、対処も 3 種類

- **症状**：止まったワーカーを機械的に再開すると、同じ壁にぶつかるだけのことがある。
- **原因**：止まった理由が違う。過負荷で落ちた（数回までなら自動で再開してよい）。利用上限で落ちた（自動で再試行してはいけない）。自分の判断で止まった（ESCALATE、予算の関門、正直な BLOCKED。人の裁定が必要）。
- **防護**：最後の出力で分類し、それぞれに決まった手順で対処する。人の裁定は、まず長期メモに書き、次に `--notify` で届け、バスの応答を読んでからワーカーを再開する。
- **このキットでは**：上限の経路は自動再試行せずにカウンタを戻す。`watch.sh` はワーカーの終わり方を分類して表示する。runbook 第 5 節に手順。`[L27]`

## L28 表が埋まった後の裁決は、次の goal に記帳されやすい。正本は台帳の本文

- **症状**：状態ファイルの「審査済み」が、実際の審査より 1 つ先の goal に付いていた。
- **原因**：境界行に goal 名がない（または `BLOCKED` の後ろにある）と記帳先を推測することになり、その時点で表はもう埋まっているので、推測は次の goal を指す。
- **防護**：goal 名は `BLOCKED` の前に書くよう指示する。最終的な集計は台帳の本文と PROGRESS で行う。
- **このキットでは**：`line_goal()` は `BLOCKED` の後ろの goal 名も受け付ける。強制審査は、飛ばされた goal の名前をそのまま使う。`[L28]`

## L29 台帳だけでは、バスが本当に審査したかが分からない

- **症状**：「問題なさそう」と書いただけのバスと、自分でテストを流し直したバスが、台帳の上では同じに見えた。
- **原因**：台帳には次の指示だけが残り、裁決の前に書かれた審査の本文が捨てられていた。
- **防護**：応答の全文を別のファイルに残す。人の監査はそちらを読む。
- **このキットでは**：`BUS-REVIEWS.md`（自動の審査のたびに全文を追記）。`[L29]`

## L30 監視は、トランスクリプトの中のプロトコル文字列を探さない

- **症状**：起動して 1 分もたたないうちに、監視スクリプトが「境界に達した」と報告した。実際には何も起きていなかった。
- **原因**：goal 包には、ワーカーに教えるためにプロトコルの行がそのまま書かれている。ワーカーが最初のターンでそれを読むので、トランスクリプトを文字列で検索すると、文書の例文に一致してしまう。
- **防護**：受け入れの判定は、成果物と hook 自身のパーサーにアンカーする。文字列を読むなら、JSON として解析し、アシスタントの行だけを行頭固定で見る。
- **このキットでは**：`watch.sh` は `--status` と、単調に増える量（台帳・審査全文・PROGRESS・トランスクリプトの大きさ）だけを見る。`[L30]`

## このキットで追加した防護

実務の実装を読み直して作り直す際に、次の点を足しました（README では「デモで追加した点」として区別しています）。

- **偽の CLI による端から端までのテスト**：`hooks/selftest/fake-claude` が CLI の代わりに応答し、hook を標準入力から退出コードと台帳まで通して検査します。実務の自己テストは関数単位でした。
- **未知の判定語を拒否**：`OK` や `Done` のような語は、実務の実装では素通りしていました。
- **最後の署名行で判定**：本文に引用された別の境界行に判定を奪わせません。
- **古い引き継ぎ書の取り違え防止**：交代のときに引き継ぎ書の指紋を比べます。存在するだけでは合格にしません。
- **新しいバスの応答確認**：起動したバスが `BUS-READY` と答えなければ切り替えません。
- **計画停止**：`PAUSE_AFTER` に書いた goal の PASS の後で意図的に止まり、`--next` で続きの指示を取り出せます。長い作業を何日かに分けるためのものです。
- **`--seed`**：バスの起動も 1 か所の呼び出しに収めました。
- **証拠門の通算ブロック数**：連続数はリセットされるので、誤ブロックの数を後から数えられるよう通算も記録します。

## 実走で見つかったこと

偽の CLI を使う自己テストでは再現できず、実際の CLI と実際のホストで初めて出たものです（toy-run と、このキットで作ったほかのリポジトリの実走）。

### hook は、CLI 自身の認証情報を受け取らないことがある

- **症状**：G0 の境界でバスを起こす呼び出しが 2 秒で rc=1 になり、リレーは設計どおり止まって人を待った。台帳には何も残らず、原因はバスのトランスクリプトにある合成メッセージ `Not logged in · Please run /login` を読むまで分からなかった。
- **原因**：共有ホストで、アカウントの MCP 設定（外部サービスのトークン入り）を読み込ませないために `CLAUDE_CONFIG_DIR` を分け、認証をホスト自身の長期トークン（環境変数）に頼った。CLI 2.1.233 の Stop hook には、`CLAUDE_CONFIG_DIR` は届いたがトークンは届かなかった。
- **防護**：hook の環境を当てにしない。バスを呼ぶ直前に、必要なものを戻すファイルを読む。失敗したときは、理由を台帳に残す。
- **このキットでは**：`GOALBUS_ENV_FILE`（`claude_call` が呼び出しの直前に読む）。起こすのに失敗したら、CLI の出力の抜粋を `BUS-LOG.md` に書き、認証の失敗ならこの設定を案内する。抜粋では URL の中の資格情報とトークン形の文字列を伏せる。`[kit]`

### 再開すると、前のプロセスの結果行が「終わった」に見える

- **症状**：`--resume` で続きから再開した直後に、監視が `[ended]` を報告する状態になっていた（実走では、監視の記録を手でそろえてから再開した）。
- **原因**：`.worker-output` には前のプロセスの結果行が残っている。監視は「結果行がある」かつ「ログの大きさが前回の報告時と違う」で終わりを判定していたので、再開の見出し行が 1 行増えただけで条件を満たした。
- **防護**：最後の見出し行（`=== … worker …`）の後に結果行があるときだけ「終わった」とする。
- **このキットでは**：`watch.sh` の `worker_finished`。`[kit]`

### 操作者の環境変数が、自己テストのサンドボックスに漏れる

- **症状**：次のリポジトリの発車で、導入時の自己テストが 6 件失敗し、発車が止まった（止まったのは設計どおり）。同じキットを同じホストで単独に走らせると、すべて成功していた。
- **原因**：発車スクリプトが `GOALBUS_ENV_FILE` を export したまま導入を走らせた。このファイルは `CLAUDE_CONFIG_DIR` も設定するので、サンドボックスの中のバス呼び出しがそれを読み、偽の CLI はトランスクリプトをサンドボックスの外に書いた。サンドボックスの hook からは見つからない。
- **防護**：操作者の実行環境を注入するための変数は、自己テストのサンドボックスに入れない。テスト全体を、わざと毒を入れた操作者の環境で走らせ、漏れれば赤くなるようにする。
- **このキットでは**：`harness.sh` の `run_in_sandbox` が `GOALBUS_ENV_FILE` を外す（必要なテストだけが `EXTRA` で渡す）。`bus-tests.sh` は冒頭で、別の場所を指す `GOALBUS_ENV_FILE` を export してから全件を走らせる。修正前の harness では、ホストと同じ 6 件が失敗することを確かめた。`[kit]`

### CI の手順を手元で確かめると、共用の環境が書き換わる

- **症状**：別のリポジトリの実走の最後の goal で、ワーカーが CI の手順を手元で確かめようとして `corepack enable` を実行した。corepack はホストで共用している Node の `pnpm` を自分の中継に差し替えたうえ、プロキシの証明書のせいで pnpm を取得できず、`pnpm` が 1 分ほど使えなくなった。ワーカーは自分で元に戻し、変更の台帳に書いた。バスはそれを確かめ、越えてはいけない線を越えたことを最後の裁決に明記した。ただし、2 つのシンボリックリンクの所有者は root から実行アカウントに変わったまま残った。戻すには root の権限が要る。
- **原因**：越えてはいけない線には「リポジトリの外に書かない」とあった。しかし、CI の準備の手順がリポジトリの外に書く命令だとは気づきにくく、CI の手順を手元ですべて確かめることは、むしろ丁寧な仕事に見える。
- **防護**：道具を入れる命令・有効にする命令を、名前を挙げて禁じる。CI の中の準備の手順は CI の上でだけ走らせ、手元ではプロジェクト自身の命令だけを確かめる。
- **このキットでは**：goal-brief のテンプレートの越えてはいけない線に 1 項目を足した。`[kit]`

## おまけ：小さな罠

- **pipefail の下の `| head` は書き手を殺す**：起動スクリプトで状態表示を `| head -n 8` で切ったところ、表示の残りを書こうとした側が SIGPIPE で止まり、`set -e` と重なってワーカーを起動する前にスクリプトごと終わった（toy-run の最初の起動）。全文を出すか、bash の中で切ります。
- **「429」は数字列の中にも現れる**：利用上限の判定に素の `429` を使うと、セッション ID（`…4291…`）や費用（`0.1429`）にも一致します。前後が英数字でないときだけ一致させます。

- **語彙は 2 層**：goal 層の裁決（PASS / REJECT / ESCALATE / DONE）と、行の判定（PASS / FAIL / BLOCKED / DEFERRED）は同じ PASS という語を共有するので、混ぜないよう明記します。
- **正規表現はテストと本体で共有する**：テスト側に同じ正規表現を書き写すと、本体を変えてもテストは緑のままになります。
- **バスも間違える**：ワーカーがコードを示してバスの説明に反論し、正しかったことがあります。証拠が決めるのであって、立場ではありません。
- **「無関係な既存の問題は直さない」と「自分の変更で入れた欠陥は直す」の境目**：ログイン後の着地点を変えた結果、別の 5 ファイル 11 箇所のハードコードが壊れました。ワーカーは最後の goal に回そうとしましたが、バスは「この goal で入れた回帰はこの goal で直す」と差し戻し、ワーカーが見落とした 11 箇所目も数え直して見つけました。
